Project Overview

This project came from a class activity that asked students to build a general LP solver for maximization problems with continuous variables — from scratch, using AI assistance. The tool had to solve any LP in standard form and display the Simplex iterations.

This page IS the project. The demo below is the live solver built for the assignment. It converts constraints to augmented form with slack variables, performs pivot operations, and halts when all objective-row coefficients are non-negative.

Building a tool that correctly runs the algorithm I had just learned reinforced every concept — especially the role of basic vs. non-basic variables and the algebraic meaning of moving between corner points.

● Simplex Method — Core Concepts
Augmented Form

Convert each ≤ constraint to an equality by adding a slack variable sᵢ ≥ 0. The initial basis consists of all slack variables with all original variables = 0. This maps to the corner point at the origin (x₁=x₂=0).

Pivot — Entering Variable

The entering variable has the most negative coefficient in the objective row (for maximization). It's the variable that increases Z the most per unit.

Pivot — Leaving Variable (Min-Ratio Test)

For the entering column, compute RHS / coefficient for every row with a positive coefficient. The row with the smallest ratio leaves the basis — preventing any variable from going negative.

Optimality Condition

The algorithm halts when all objective-row coefficients ≥ 0. At this point, no variable can improve Z — we are at the optimal corner point.

Evidence
AI Conversation — Solver Construction
Student Prompt
Build me a general LP solver in vanilla JavaScript for maximization with ≤ constraints. It should: (1) take objective coefficients and an A-matrix/b-vector as input, (2) add slack variables to build the augmented form, (3) iterate the simplex pivot using the most-negative-coefficient entering rule and min-ratio-test leaving rule, (4) return the optimal x values, Z, and each tableau step so I can display them. No libraries.
Follow-up: Debugging
The solver returns Z=30 for the street food problem but the correct answer is Z=38. What went wrong?
Assistant Response
Here's a complete vanilla JS implementation. The key insight is representing the tableau as a 2D array where the last row is the objective and the last column is the RHS. findEnteringCol scans the objective row for the most negative value. findLeavingRow applies the min-ratio test, skipping rows with non-positive pivot column entries to avoid division by zero...
Bug Fix
The issue is in the objective row setup. The initial objective row should store negated coefficients (-c[j]), not the raw values. Using +c[j] triggers the optimality condition too early — the solver stops at a sub-optimal corner without crashing.

What Did I Learn?
Dimension 01

Knowledge

  • Augmented form: slack variables turn each ≤ into an equality, making LP matrices square enough for the simplex to operate
  • The objective row stores negated coefficients — the algorithm reads Z from the RHS after pivots accumulate it
  • Every simplex iteration moves from one corner point to an adjacent, strictly better one
  • The min-ratio test prevents basic variables from going negative (infeasible) during pivots
  • The algorithm terminates in finite steps for non-degenerate LPs — proven by the strict improvement at each pivot
  • Binding constraints at the optimal define the active edges that intersect at that corner point
Dimension 02

Skills

  • Writing precise algorithmic prompts — vague prompts produce wrong code; the min-ratio test must be specified explicitly
  • Debugging numerical code by tracing through a known example by hand (the street food problem)
  • Packaging a complete tool as a single, zero-dependency HTML file
  • Implementing canvas-based 2D visualizations: feasible region polygon, constraint lines, corner points
  • Separating concerns in JavaScript: solver logic vs. UI vs. drawing
  • Reading and verifying a simplex tableau: identifying basic variables from the identity submatrix
Dimension 03

Reflection

The most surprising part was how a single sign error (+c vs −c in the objective row) produced a wrong but plausible-looking answer. The solver didn't crash — it just stopped early. This taught me that verifying AI-generated numerical code against hand-calculated examples isn't optional — it's the only way to catch subtle bugs.


Building the tool also made the Simplex Method feel concrete. Reading about "pivot operations" was abstract, but writing the row-reduction code line by line forced me to understand exactly what each pivot does to the tableau and why.


Real-world application: production LP solvers (CPLEX, Gurobi) use the exact same simplex logic, but extended with revised simplex, dual simplex, and branch & bound. The core pivot rule I implemented is unchanged from Dantzig's 1947 original.
